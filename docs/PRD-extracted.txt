4. 主流程与状态机
4.1 新用户 Onboarding
注册 → 同意协议 → 创建 Dog Profile → 完成 PawStyle 问卷 → 获取结果 → 进入 Solo 或 Pack。测试可以暂存；若 E/P 不完整则结果标为“风格待补充”，不得伪造完整分类。
4.2 Solo Walk 订单
Owner 选择狗与时段 → 创建 requested 订单 → Admin 确认与指派 assigned walker → confirmed → Walker 接狗后 in_progress → 完成归还并提交报告 completed。例外：requested/confirmed 可按规则 cancelled；异常服务可标记 incident_review。
4.3 Pack 加入与活动
Owner 浏览 Pack → 提交 application → safety_review → 如有需要 intro_scheduled → 记录 intro_result → approved / rejected / needs_more_info。通过后才建立 pack_membership，允许报名对应 Pack 活动；审核不通过不得加入。
4.4 重要状态矩阵

7.1 重要约束与隐私规则
同一个 dog_id 下允许多次 Assessment Session，历史不得覆盖；item_code 唯一避免重复答案。
所有状态更新通过后端事务；对预约库存、Pack 最大人数做并发保护。
涉及 Pack 的审核事件、攻击事件与健康备注不公开在普通成员列表或分享卡。
Walk Task 的 booking_type + booking_id 指向 Solo 或 Pack Event Booking：实现时建议通过独立关联表或严格应用层校验保证引用一致性。
完整问卷原始数据与计算结果分存，支持版本回溯和重新评分；未经许可不公开。
若面向中国大陆实际商业上线，需要进一步评估适用的个人信息、用户同意及运营合规要求；本 PRD 不代表法律审查。

9. 验收测试与 Definition of Done
□ 新用户可注册、创建 1 只狗，资料保存且重新登录仍存在。
□ 可完成全部 B/D/S 问卷；中断后恢复草稿；D 的 X 能被正确识别。
□ 四类、混合、待补充和分界提示通过预定义单元测试。
□ 用户能够预约开放 Solo 时段，不能重复抢同一名额。
□ Pack 申请需先审批；存在事件须人工处理；未通过不能入组。
□ 遛狗师只能看到自己的任务，并能完整打点交接与提交报告。
□ 完成任务后生成可追溯报告和站内通知；管理员可查操作记录。
□ 未授权用户无法访问其他主人订单、测试答案和敏感事件。
□ 分享卡不泄漏电话、精确地址、健康/攻击事件。
□ 全部关键异常有反馈：断网、重复提交、时段售罄、资料不完整、审核拒绝。

11. 待确认问题（会议决策清单）
□ 是否只支持邮箱注册，还是接短信验证码？
□ Solo 每次预约允许几只狗？价格是否只展示、不收款？
□ Pack 是固定时间周期活动还是每次独立开放报名？
□ 首见是否全部必需，还是仅风险审核后决定？
□ 取消规则、改期权限与迟到处理怎样定义？
□ 是否允许用户删除测试历史？数据留存多久？
